# vcows-deploy v0.1.0.0 — tooling survey, second pass

Surveyed 2026-08-30 on `feature/scaffold` at `6497f30`, by three agents plus this
orchestrator. Nothing in the repository was modified.

This is a follow-on to `docs/tooling-2026-08-29.md`, not a replacement. That survey
ran against a repository with no automation at all; the CI layer, `justfile`,
pre-commit, coverage config, trivy/syft scanning and cosign signing it recommended
have all since landed. Re-running the same questions would mostly re-derive its
answers, so this pass covers three things instead: what the first survey deferred,
what has changed underneath it, and one axis it did not consider at all — the
configuration of the agents doing the work (section 5).

Where a claim was measured in this session it says so. Where it comes from
research rather than a local run, it says that too, and section 7 lists what could
not be confirmed either way.

## 1. Verdict

**The conventional tooling surface is close to exhausted, and the remaining gap is
a test class rather than a linter.**

The first survey's section 5 rejected nine tools with measurements, and this pass
confirms every one of them, in two cases with better evidence than it had (6.1,
6.2). Nothing generic is left to add. What the repository still cannot do is boot
a guest and check the result, and the single defect that most deserved catching —
`docs/acceptance.md` defect 5, two guests booting healthy on the wrong addresses
with `cloud-init status: done` — is in exactly that blind spot. Section 4.1 is the
recommendation that matters.

Against that, section 2 is a delivery defect rather than a tooling item, and it is
the thing to fix before anything ships: **the artifact `just sign` signs is not the
artifact the README says is delivered.**

Section 5 is new ground. The repository carries no `CLAUDE.md`, no project skills,
no hooks and no agent configuration, while its most important operating rules —
the `--system-site-packages` trap, the non-declarative config, the CVE baseline's
destructible rationale block — are exactly the kind an agent gets wrong by being
helpful.

## 2. Act before the next delivery: the signed artifact is not the delivered one

**Measured.** `scripts/sign.sh:32` signs `.cache/scan/image.tar`, and that file on
this box is **444,472,320 bytes** — the uncompressed docker-archive that
`scripts/image-scan.sh:36` writes with `podman save --format docker-archive` so
trivy and syft can both seek it.

`README.md:247` describes the delivery as **"~152 MB as a delivered `podman save |
gzip` tarball."**

Those are two different byte streams and both are called "the delivery tarball."
A site handed the 152 MB gzip and the `.bundle` produced from the 444 MB archive
cannot verify anything, and the failure is a signature mismatch, which reads as
tampering rather than as a packaging bug.

Three further facts make this a section 2 item rather than a one-line fix:

1. **Nothing calls `just sign`.** `.github/workflows/image.yml:56` ends at
   `just scan`. `just sign` and `just verify-signature` (`justfile:83-89`) are
   invoked by no pipeline on either platform, so the signed bundle only ever
   exists in one developer's gitignored `.cache/`.
2. **Nothing leaves CI.** There is no `upload-artifact` in any workflow. `just scan`
   writes `trivy.json`, `sbom.spdx.json` and `image.tar` into `.cache/`, and the
   runner deletes them. The monthly `rebuild-scan` in `scheduled.yml` therefore
   proves something and records nothing, which removes the one reason to run it
   monthly: diffing this month's SBOM against last month's across an unpinned
   `dnf -y install` layer.
3. **The SBOM is unsigned and unbound.** It ships as a loose file beside the
   archive. A loose SBOM can be swapped, or paired with the wrong tarball, and the
   site has no way to tell.

The remedy is to fix one archive format, sign that, bind the SBOM to it with
`cosign attest-blob` (4.2), emit a `SHA256SUMS`, and have a pipeline produce the
whole bundle as an artifact. For an air-gapped handover the bundle *is* the
product, and its assembly currently exists only in the author's head.

## 3. Defects found while surveying

### 3.1 · `uv.lock` is committed, watched by dependabot, and installed from nowhere

`justfile:22` runs `uv pip install -e . --group dev` — an unconstrained resolution
against the `>=` bounds at `pyproject.toml:44-57`. `uv.lock` is referenced in
exactly four places, all of them cache keys: `ci.yml:33`, `ci.yml:51`,
`.gitlab-ci.yml:33`, `.gitlab-ci.yml:57`. Nothing installs from it, so the
dependabot PRs that update it modify a file no install path reads.

Every other input to this build is pinned by digest: seven tool binaries
(`install-tools.sh:33-44`), the base image, the tofu RPM and the provider
(`Containerfile:44-69`). The development toolchain is the one exception, which
means a ruff or pytest release can turn a green PR red for reasons unrelated to
the PR.

`pyproject.toml:26-34` explains correctly why `uv sync` cannot be used here. That
argument does not extend to `uv export --format requirements-txt` followed by
`uv pip install -r` into the same `--system-site-packages` venv, which preserves
the flag and honours the lock. See 4.3.

### 3.2 · There is no LICENSE file

**Measured:** no `LICENSE*` and no `COPYING*` in the repository root.

The project vendors a third-party licence (`licenses/dmacvicar-libvirt/`),
computes an aggregate SPDX expression for the image (`Containerfile:71-78`),
publishes a source URL in its OCI labels (`Containerfile:176`), and devotes a
README section to the GPLv2 §3 source-sidecar obligation (`README.md:259-271`) —
and states no licence for its own code. For something redistributed to a
third-party site as a tarball, the surrounding licensing work makes the omission
conspicuous rather than merely untidy.

### 3.3 · The project's own standard is not applied to its GitHub actions

`scripts/install-tools.sh:6-11` argues explicitly against marketplace actions:
`astral-sh/setup-uv@v3` is "a mutable tag running somebody else's code on the
runner with the job's token." Ten `uses:` lines across the three workflows then
pin `actions/checkout@v4` and `actions/cache@v4` — mutable tags — with the default
broad `GITHUB_TOKEN` and no `permissions:` block anywhere.

Being first-party does not change the argument the script makes. Dependabot
already watches `github-actions`, so digest pins stay maintained without manual
work.

A second gap in the same files: no `timeout-minutes` on any job. `orchestrator/tofu.py`
deliberately gives `plan` and `apply` no timeout, so a wedged test double hangs a
runner to GitHub's six-hour limit. The first survey deferred pytest-timeout "until
CI exists" (`tooling-2026-08-29.md:461-464`); CI now exists, and `timeout-minutes`
is the cheaper of the two levers.

### 3.4 · gitleaks runs nowhere except one developer's pre-commit

`pre-commit` appears in no `justfile` recipe, no script, and neither pipeline;
`README.md:281` calls installing it "Optionally." The gitleaks hook scans the
staged diff, not the tree and not history.

Hygiene is correct today — `git log --all --diff-filter=A` shows no key material
has ever been committed, `.cache/` is gitignored (`.gitignore:30`) and
`.cache/cosign.key` is mode 0600. But the stated risk surface is `ssh_keyfile` and
`known_hosts` paths, a run directory documented as holding cleartext credentials
indefinitely, and now a cosign private key living in the working tree. Nothing
would catch tomorrow's mistake.

### 3.5 · The GitLab runbook contradicts a decision made two commits later

`docs/ci.md:146` instructs the migrator to "create two pipeline schedules: monthly
with `REBUILD_SCAN=1`, weekly with `MUTANTS=1`." No job in `.gitlab-ci.yml` reads
`$MUTANTS`, and `.github/workflows/scheduled.yml:3-6` explains at length why
mutation testing is deliberately absent from every pipeline. This repository lints
for exactly this class of drift, which is why one line of it belongs on this list.

### 3.6 · A wrong rule name in the previous survey

`tooling-2026-08-29.md` §5.3 names the tflint rule `terraform_comment_style`. That
rule does not exist; the real name is **`terraform_comment_syntax`**. The verdict
is unchanged — see 6.1 — but a `.tflint.hcl` written from the current text would
silently no-op rather than disable the rule it names.

## 4. Adopt

Ordered by leverage.

### 4.1 · T1 — A TCG-backed end-to-end gate, on hosted runners

**This is the recommendation of this survey.**

`terraform-provider-libvirt`'s own CI runs acceptance tests against a real
libvirtd on unmodified `ubuntu-latest`. Read from its live `.github/workflows/test.yml`:

```
apt-get install -y qemu-system-x86 qemu-utils \
                   libvirt-daemon-system libvirt-clients libvirt-dev
systemctl start libvirtd     # qemu.conf: user/group root,
                             # dynamic_ownership=0, security_driver=none
virsh -c qemu:///system pool-define-as \
      --name default --type dir --target /var/lib/libvirt/images
TF_ACC=1 TF_PROVIDER_LIBVIRT_DOMAIN_TYPE=qemu make testacc
```

against a cached tiny Alpine qcow2, for both Terraform and OpenTofu, inside a
30-minute timeout.

**`TF_PROVIDER_LIBVIRT_DOMAIN_TYPE=qemu` swaps `type='kvm'` for `type='qemu'`, so
no `/dev/kvm` is required.** It behaves identically on GitHub-hosted and GitLab.com
SaaS runners, which matters because GitLab is the destination. This is real
`virStorageVolUpload`, real libvirtd, real domain define/start/undefine — the three
things every mock in this repository has to stand in for.

Why it earns the top slot: `docs/acceptance.md` defect 5 was `routes: [{to: default}]`
producing two guests that booted **healthy on the wrong addresses**, reporting
`cloud-init status: done`. No mock provider, no `tftest.hcl` assertion and no
`tofu plan` can observe that. A smoke test that boots a tiny image and asserts the
address is the only gate class that could, and it is the one gate class the
repository does not have.

Scope it as a smoke test, not as the rig gate. The rig gate
(`tests/test_libvirt_rig.py`, `VCOWS_RIG_URI`) stays a documented named skip for
the reasons at `tooling-2026-08-29.md:487-497`; this is a third thing, between the
mocked module test and the hardware rig. Roughly half a day, and the recipe is
copyable.

### 4.2 · T2 — `cosign attest-blob` for the SBOM

Binds `sbom.spdx.json` to the artifact with the same key and the same offline
verification flow the tarball already uses:

```
cosign attest-blob --predicate sbom.spdx.json --type spdxjson \
       --key ... --signing-config ... --bundle sbom.bundle
```

verified with `cosign verify-blob-attestation`. One command in `scripts/sign.sh`,
one in its `--verify` branch, one line in the delivery docs. Fold it into the
section 2 fix rather than doing it separately.

Two things confirmed while checking this, both of which say the existing script is
already right:

* **cosign v3.0.4 shipped "Don't require a trusted root to verify offline with a
  key" (#4613).** That is upstream confirming the local-key + `--bundle` +
  `--insecure-ignore-tlog` pattern at `sign.sh:38-39` is the supported offline path,
  not a workaround.
* **`--offline` was deprecated as a no-op in v3.0.3 (#4457)** because it never meant
  "no network." Do not add it.

`install-tools.sh` pins cosign 3.1.3, which is the current release and is itself a
security fix (GHSA-fx35-mq7g-6g98, a verification bypass via an unexpected public
key in a legacy bundle). The v3.1.1 breaking change most likely to bite a script —
bundle output or registry upload now strictly required with the new bundle format
(#4785) — does not apply, because `sign.sh` passes `--bundle` on every path.
Deprecations to know about before they become v4 removals: `--payload`,
`--output-attestation`, `--certificate`/`--ca-roots`/`--certificate-chain`,
`cosign triangulate`, `cosign copy`.

### 4.3 · T3 — Install from the lock, and pin `ty` exactly

The 3.1 fix: `uv export --format requirements-txt` into a generated file,
`uv pip install -r` it inside the `--system-site-packages` venv that `just dev-env`
already creates, and add a lint gate asserting the export is current. That keeps
the flag, honours the lock, and makes the dependabot PRs mean something.

Separately, `pyproject.toml:52` pins `ty>=0.0.75`. ty is still 0.0.x and its own
documentation still says breaking changes may occur between any two versions, so
that bound lets an arbitrary future breaking release into the only type gate this
project has. Tighten it to `~=0.0.75` or an exact pin.

### 4.4 · T4 — `trivy fs --scanners vuln --include-dev-deps`

The only Python-side scanning gap that matters here is a CVE in *development*
tooling: the three declared runtime dependencies ship as RPMs and are already
covered by trivy and syft against the image. Trivy has parsed `uv.lock` natively
since 0.59.0, so this is **zero new tools and no second offline database** — one
line in `scripts/image-scan.sh`, or a `just audit` recipe.

osv-scanner has the only genuinely good offline database mode, but it means a
second binary and a second DB mirror to maintain. pip-audit and safety are both
worse fits. If 4.4 is adopted, none of the three is needed.

### 4.5 · T5 — `.shellcheckrc`, and shfmt

782 lines of bash across ten scripts get correctness checking (`scripts/lint.sh:112`,
`shellcheck -x -s bash`) and no formatting check, while Python gets both. There is
no `.shellcheckrc`, so every optional check is off.

The optional checks worth turning on for an install/build/sign path:

| Check | Why here |
|---|---|
| `check-extra-masked-returns` | Masked non-zero exits — the silent-failure class this project already cares about |
| `check-unassigned-uppercase` | Typo'd env-var names, and versions and digests travel as uppercase vars |
| `require-variable-braces` | Consistency, cheap |
| `quote-safe-variables` | Ditto |
| `avoid-nullary-conditions` | Ditto |

`deprecate-which` is already satisfied: `lib.sh:have()` uses `command -v`.

shfmt closes the formatting asymmetry. It has no Fedora or EPEL package, so vendor
the static binary the way `install-tools.sh` already vendors six others. One
gotcha: **passing any shfmt CLI flag disables `.editorconfig` entirely**, so pick
one configuration mode and stay in it. Budget a one-time normalisation pass.

Note that EPEL 9 ships shellcheck 0.10.0 against upstream 0.11.0, which argues for
vendoring shellcheck alongside the others rather than taking whatever `os-deps.sh`
finds — otherwise the new checks are available on the maintainer's box and not in
CI.

### 4.6 · T6 — `--source-date-epoch` and `--rewrite-timestamp`

**Verified on this box** (podman 5.8.2, buildah 1.43.2, Rocky 10.2):
`--source-date-epoch`, `--rewrite-timestamp` and `--timestamp` are all present in
`podman build --help` and `buildah build --help` today. `--timestamp` and
`--source-date-epoch` are mutually exclusive; `--rewrite-timestamp` pairs with the
latter and clamps in-layer file mtimes down to the epoch.

**This does not make the build reproducible, and §5.7's rejection stands.** It does
not touch tar entry ordering, rpmdb ordering, or dnf resolver nondeterminism; only
a lockfile-based approach such as rpmoci addresses those, and that is a different
build. What it buys is that two builds from the same commit differ only where dnf
genuinely drifted, instead of also differing in every timestamp — which makes the
monthly rebuild-and-scan diff readable. Adopt it as diff hygiene, one line in
`scripts/image-build.sh`, and do not let it become a reproducibility claim.

### 4.7 · The smaller items

* **CI hygiene from 3.3 and 3.4.** Digest-pin the four distinct actions, add a
  minimal `permissions:` block, add `timeout-minutes`, add `just secrets` running
  `gitleaks detect --no-banner` over the full tree and put it in `check`. A
  `pre-commit run --all-files` job would pick up `check-yaml` for free.
* **`actions/upload-artifact`** for `trivy.json`, `sbom.spdx.json` and the delivery
  bundle. It is a `uses:`, so `workflows_carry_no_logic()` in `scripts/lint.sh`
  still passes.
* **A `just cov` recipe.** `pyproject.toml:62-72` configures branch coverage,
  `source`, `exclude_also` and `fail_under = 90` with a comment recording 96%
  measured — and `--cov` appears in no recipe, script or pipeline. `docs/ci.md:58-65`
  argues well against a *blocking* gate; that argument does not justify having no
  way to produce the number. Keep it out of `check`.
* **A second `run` block in `tests/libvirt-module.tftest.hcl`.** The first survey
  named the two uncovered branches itself (`tooling-2026-08-29.md:507-512`):
  `base_volume.create == false` falling back to `var.base_volume.path`, and
  `devices.interfaces[*].source.bridge`. The bridge branch is the one a real RHEL 9
  site is most likely to take. Test work rather than tooling, but cheap and it uses
  the existing pattern.
* **actionlint.** Neither `just lint` nor pre-commit validates workflow *semantics*;
  `check-yaml` covers well-formedness only, locally. Modest value across three small
  stable workflows, and it does nothing for `.gitlab-ci.yml` — which by its own
  header has never been executed and remains the larger unvalidated surface.
* **`.editorconfig` and `LICENSE`.** The second is 3.2 and has legal weight. The
  first only covers shell, YAML and Markdown once ruff and `tofu fmt` have taken
  Python and HCL, and only for editors that read it; worth it when a second
  contributor arrives, not before.
* **`--annotation` on the image build.** `LABEL` writes the image *config*;
  OCI annotations live in the *manifest*, and podman does not mirror one to the
  other. An auditor running `skopeo inspect` on the delivery tarball without loading
  the image reads the manifest and sees none of the fifteen labels
  (`Containerfile:168-183`). Mirroring `created`, `revision` and `base.digest` is
  three flags. Optional, and only if anyone downstream actually does that.

## 5. The agents are unconfigured

This axis did not exist in the first survey. It should have.

The repository contains no `CLAUDE.md`, no `.claude/skills/`, no `.claude/agents/`,
no `.claude/hooks/`, no `.claude/commands/` and no `.mcp.json`. The single project
file is `.claude/settings.local.json`, holding three permission entries.

That matters more here than in most repositories, because this project's operating
rules are almost all counterintuitive, and an agent that does the obvious helpful
thing breaks them.

### 5.1 · A project `CLAUDE.md` — the highest-value item in this section

Eight facts, each a pointer plus the one sentence that makes the pointer worth
following. Target ~120 lines.

1. **The `--system-site-packages` trap.** `pyproject.toml:30-34`: without the flag
   the RPM binding is invisible, and without the explicit interpreter uv installs
   its own CPython whose site-packages contains no RPMs at all, "so the flag appears
   to work while `import libvirt` still fails." The only correct incantation is
   `just dev-env`. **Never `uv sync`.** And this is not rig-only —
   `tests/fake_libvirt.py` imports libvirt at module scope.
2. **The config is not declarative.** `README.md:7`. vcows never converges; `deploy`
   creates and reports, never modifies, never removes. Identity is the marker in
   `<metadata>`, never the name.
3. **CI calls `just` recipes and nothing else.** `scripts/lint.sh:34-77` parses both
   pipeline files with PyYAML and rejects any command outside the allowlist, so
   adding a `run:` step fails `just lint`. New logic goes in `scripts/`, gets a
   recipe, and the recipe gets called.
4. **Gate discipline.** `tests/conftest.py:7`: "A gate that quietly passes because
   it did not run is worse than no gate." Every skip goes through `conftest.gate()`
   or `conftest.require()`; `tests/test_gates.py` AST-walks the suite and fails on
   any bare `pytest.skip`, `importorskip` or `mark.skip`. Gate names are a closed
   set, and `VCOWS_GATES` is case-sensitive and does not strip whitespace.
5. **Commit style, and never a co-author.** An imperative sentence-length subject,
   and a body saying what was *measured*, correcting prior wrong claims by name.
6. **`docs/cve-baseline.json` is a differential gate, not a list to append to.**
   Every group carries `why` and `recheck`, and the accept/reject decision turns on
   **reachability** — the x/crypto acceptance rests on `render.py:61` using
   `qemu+sshcmd`, whose dialer execs OpenSSH and never enters `x/crypto/ssh`.
   Critically: **`scripts/image-scan.sh --write-baseline` destroys the rationale
   block**, regenerating a fresh object with only `image`, `generated`, `note` and
   `accepted`. A new finding is a hand-edit.
7. **Four pins nothing can automate.** `BASE_DIGEST`, `TOFU_RPM_SHA256`,
   `PROVIDER_SHA256`, and the `h1:` in `docs/provider-0.9.8.lock.hcl`.
   `tooling-2026-08-29.md` §5.6 measured that Renovate cannot recompute any of them.
   `just verify-provider` is the gate that catches a half-finished bump.
8. **Point at the two ledgers.** `tooling-2026-08-29.md` §5 and
   `docs/review-2026-08-29/2026-08-29-remediation-checklist.md`. An agent proposing
   grype, tflint, checkov, terraform-docs, bandit or `VCOWS_GATES=all` is
   re-deriving settled work.

### 5.2 · Three skills worth authoring

* **`delivery`.** There is no `just deliver`; the sequence exists only as prose
  across `docs/ci.md`, `README.md` and the justfile. The order is load-bearing
  (`sign` refuses without the archive `scan` writes), the GPL source-RPM medium is
  the step a human forgets, and section 2's format mismatch is exactly what a
  written-down sequence surfaces.
* **`cve-triage`.** Encodes fact 6 above. A skill beats a doc here because the
  failure mode is an agent doing the obvious helpful thing — rerunning
  `--write-baseline` — and silently deleting the reasoning.
* **`provider-bump`.** The four-place check, the schema diff against
  `docs/provider-schema-0.9.8.json`, the mirror rebuild, the CVE re-triage that
  follows, and the cache-key trap: keyed on `main.tf`, **not** on the versioned lock
  filename, because a bump renames that file and `hashFiles` collapses to a
  constant. `docs/ci.md` calls this "a step in a runbook"; this is that runbook,
  executable.

Not worth authoring: an air-gap verification skill. `tests/test_image.py` under
`--network=none` already is that verification, and §5.5 records why a wrapper adds
nothing.

### 5.3 · Hooks

Highest value by a distance: a `PreToolUse` hook denying reads of
`.cache/cosign.key`. It is a real private key in the working tree — gitignored and
0600, but nothing stops an agent from `cat`-ing it into a transcript.

Then, in order: `just lint` on edits to `.py`/`.sh`/`.tf`/`Containerfile`; a
non-blocking warning on `docs/cve-baseline.json` edits restating fact 6; and a
write-block on `.cache/` and `.tools/`, both gitignored build scratch that no gate
can explain state in.

Not a `Stop` hook running `just check`. The suite is 24 s, two tests shell out to
the real `tofu` binary (5.81 s + 5.58 s per `--durations=10`), and `just check` also
runs `ty` and six lint gates. `just check` exists to be run deliberately.

### 5.4 · MCP servers: add none, and drop some

Researched against the current catalogue. Every infrastructure MCP server
evaluated — Terraform (first-party, but 35+ tools mostly for HCP workspace
mutation, and no OpenTofu support), OpenTofu (right shape, but this project has one
pinned provider at one frozen version), libvirt (nine hobby repos, the best with a
single star, none read-only), podman (a personal repo, 7 of 13 tools mutate),
Trivy (first-party, no commits since 2025-12), OSV, cosign, syft — is a live HTTP
client.

**That is the finding, not the individual verdicts.** For a project whose defining
constraint is air-gapped operation against pinned versions and a committed
baseline, each one moves determinism out of this repository and onto someone else's
API. Add zero.

Of what is enabled today: `context7` earns its place — this repository is
repeatedly burned by stale documentation (`docs/ci.md`: "Two things about cosign 3
that an older write-up will not mention"; `sign.sh:56-57` says the same), and
version-specific lookup is precisely that failure. `serena` does not: symbol-level
navigation pays off at 100k lines, not at 4,328 across ~20 files, and its write
tools are a second edit path with no benefit. The GitHub MCP server exposes no
Actions tools, and reading CI failures is the one GitHub thing that matters here;
`gh run view --log-failed` does it.

`pyright-lsp` is inert: it was installed 2026-08-30 and `command -v pyright` returns
nothing, because the plugin ships only a README telling you to install the binary.
Installing it would re-litigate §5.6's measured conclusion that mypy and pyright hit
the identical untyped-`libvirt.py` ceiling `ty` already hits.

### 5.5 · The permission allowlist has the wrong three entries

`.claude/settings.local.json` allowlists `uv venv *`, `uv sync *`, `uv run *`.

**`uv sync` is the one uv subcommand this project documents as unusable**
(`pyproject.toml:33`) — running it builds a venv without `--system-site-packages`
and breaks every libvirt import. Remove it. The other two use a space where the
pattern syntax wants a colon (`Bash(uv venv:*)`).

Worth adding, all read-only or idempotent: `just:*`, pytest, ruff, `ty check`,
shellcheck, hadolint, `tofu fmt|validate|version`, `podman images|inspect`,
`gh run list|view`. Worth *not* adding, because each mutates something expensive or
irreversible: `just image|scan|sign|mirror`, `podman build|save|rmi`,
`tofu apply|destroy`, and anything touching `.cache/cosign.key`.

## 6. Rejected, with the reason

Everything in `tooling-2026-08-29.md` §5 is re-confirmed. Recorded here are the two
where this pass found better evidence, and the items that are new to this survey.

### 6.1 · checkov, trivy config, tfsec, KICS — now measured, not inferred

The first survey concluded from reading that none of these ships a libvirt rule.
This pass measured it: GitHub code search for `libvirt` and for `libvirt_domain`
against `aquasecurity/trivy-checks`, `bridgecrewio/checkov` and `Checkmarx/kics`
returned **0 hits across all six queries**, with an unscoped control search
returning 90 hits to prove the queries worked.

Two additions:

* `trivy config` does **not** run the secret scanner (that is
  `trivy fs --scanners secret`), so the one residual "free, might as well" argument
  for pointing it at the `.tf` files does not exist. gitleaks covers secrets.
* KICS has a second disqualifier independent of rule coverage: no engine release
  since 2024, plus a Checkmarx supply-chain incident disclosed as beginning
  2026-03-19 that distributed malicious KICS images via DockerHub. The incident
  scope was **not independently verified here**; for a project with this
  repository's pinning discipline it settles the question regardless.

### 6.2 · tflint — same verdict, sharper reason

Not "it will break on OpenTofu syntax" — the one confirmed parser break is
provider-block `for_each`, which this module does not use. The reason is that 19 of
the bundled ruleset's 20 rules already pass by construction, and the twentieth is
`terraform_comment_syntax` (see 3.6), which would flag essentially every comment in
the module because the codebase deliberately uses `//`.

### 6.3 · `test:///default` — a hard blocker, source-confirmed

libvirt's `src/test/test_driver.c` `virStorageDriver` ops table has
`storagePoolCreateXML` and `storageVolCreateXML` and **no `storageVolUpload`,
`storageVolDownload` or `storageVolResize` entries at all**. `virStorageVolUpload`
is exactly how the provider pushes the golden qcow2. A search across all 160
issues and PRs in the provider repository found zero references to `test://`.

This is structural, not a limitation to work around, and it is why 4.1 uses real
libvirtd with TCG instead. The same search found that nobody in libvirt itself,
kubevirt, kcli, virt-manager or ansible `community.libvirt` uses `test://` for CI
either: it is real libvirtd on hosted runners, or self-hosted runners with real
hardware.

vagrant-libvirt (plugin last pushed 2024-08) and testcontainers-python 4.15.0 (no
libvirt module, none planned) are skips for the ordinary reasons.

### 6.4 · SLSA, in-toto, keyless cosign, build attestations

All derive their value from verifiability at consumption time, and the consumer
here has no network, no TUF root and no Rekor — `sign.sh:7-14` records both failure
modes as measured under `unshare -rn`. GitLab's SLSA provenance is Ultimate-tier,
feature-flagged, and GitLab's own documentation calls it not production-ready;
since `.gitlab-ci.yml` is the destination, building on the GitHub-only
`actions/attest-build-provenance` path would add a second attestation system that
gets deleted at the migration, contradicting the rule that `.github/` holds no
mechanism.

The only worthwhile increment is 4.2, which uses the key and the flow already in
place.

### 6.5 · OpenTofu OCI provider mirrors

The syntax is confirmed to exist:

```hcl
provider_installation {
  oci_mirror {
    repository_template = "example.com/providers/${namespace}/${type}"
    include             = ["registry.opentofu.org/*/*"]
  }
}
```

Three blockers. **`tofu providers mirror` cannot write to an OCI registry** — the
RFC defers that tooling — so you would hand-roll an `oras` push and keep
`scripts/mirror.sh` anyway. No version or stability label is stated; the
documentation lives under the 1.13.x beta tree. And **whether an OCI-sourced package
produces the same `h1:` hash as a filesystem-mirror-sourced one is undocumented**,
which is precisely the trap `docs/provider-0.9.8.lock.hcl` and
`tofu providers lock -fs-mirror=` already exist to work around. Both 1.12.6 and
1.11.14 shipped OCI-registry security fixes within the last month.

Revisit after 1.13 GA, and only after someone tests the lock-hash behaviour
directly.

### 6.6 · mutmut, and what to do instead

The failure documented at `pyproject.toml:89-108` is a known upstream class:
[boxed/mutmut#486](https://github.com/boxed/mutmut/issues/486) is open (2026-03-29,
"copies source to temp dir, breaking editable-install imports"), its fix PR #487
was **closed unmerged**, and #416, #381, #370 and #457 were closed without a
structural fix. Nothing after 3.7.0 addresses it.

The workaround usually proposed is adding a `pyproject.toml` to `also_copy` so
pytest never searches outside `mutants/` for config. Reading the installed 3.7.0
source makes that **weaker than it looks**: `execute_pytest` (`__main__.py:441`)
already passes `--rootdir=.` with cwd set to `mutants/`, so `testpaths = ["tests"]`
resolves to `mutants/tests` and the rootdir-climb explanation is partly blocked.
Confirmed from the same source: `walk_all_files()` copies only `source_paths`, so
`pyproject.toml` is genuinely absent from `mutants/`, and mutmut carries its own
diagnostic for this failure family at `__main__.py:1289`. Also worth noting,
`container/` has no `__init__.py` while `tests/` and `orchestrator/` do, which
changes where pytest's prepend-mode inserts into `sys.path`.

Practical read: the `also_copy` experiment is worth fifteen minutes as a hypothesis,
not as a fix. If it fails, **cosmic-ray 8.7.0 is the structural alternative** — it
mutates the AST in place rather than copying the tree, so this entire bug class
cannot arise. mutatest 3.1.0 is stale and there is no credible new entrant.

Either way this stays off every pipeline, for the reasons `scheduled.yml:3-6`
already gives.

  Anchore on 2025-08-29**.
* **refurb** — the working assumption that it was archived is wrong; 2.3.1 shipped

* **deptry, bashate, mypy/pyright, terraform-docs, container-structure-test,

## 7. Not confirmed, and not investigated

Recorded so nothing here is mistaken for a measurement.

* **`/dev/kvm` on GitHub-hosted runners.** Present on standard `ubuntu-latest` since
  a runner-image update around 2024-01-17 (needs a udev rule), but
  [actions/runner-images#12933](https://github.com/actions/runner-images/issues/12933),
  asking GitHub to confirm it formally, is still open and unanswered. Do not build a
  gate on it. This is moot for 4.1, which does not need KVM.
* **Whether rootless and rootful podman builds of the same Containerfile produce
  identical content.** Undocumented; needs a side-by-side test. Relevant only if CI
  moves to rootless podman on RHEL — in which case note that `podman system migrate`,
  the standard fix for subuid/subgid errors, **wipes all images, containers and
  build cache for that user**, and that podman 6.0 dropped slirp4netns so pasta must
  be present.
* **Whether UBI9 or UBI10's curated AppStream ships `libvirt-client`.** One
  `podman run --rm registry.access.redhat.com/ubi10/ubi dnf list libvirt-client`
  closes the "why not UBI" question permanently if anyone asks again. Rocky 10 stays
  the right base regardless: libvirt's documented RPC compatibility guarantee means
  there is no correctness argument for matching the target's RHEL 9 vintage, and the
  three-way size benchmark (152/134/118 MB) already settled the variant question.
  One operational note — **Rocky maintains only the current minor**, 10.0 is already
  EOL and 10.2 is current, so `BASE_DIGEST` needs periodic re-pinning rather than
  pin-and-forget.
* **The Checkmarx incident scope** (6.1).
* **Old-daemon coverage.** `download.rockylinux.org/vault/rocky/9.0/` is live (9.0
  through 9.7), and a Containerfile pointing dnf at the vaulted repos with
  `versionlock` on `libvirt-daemon-kvm` would reach libvirt 8.0.0/8.5.0 — the only
  route to the daemon versions `destroy.py`'s `undefine_mask` gate exists for, since
  Rocky 9.8 ships 11.10.0, the same as the container's client. libvirtd's control
  plane never touches `/dev/kvm`; only starting a `type='kvm'` domain does. Running
  libvirtd in a container needs `--privileged` or targeted caps, and rootless is not
  well supported. Real work, narrow surface, and nothing else reaches it. Not
  attempted here.
* **Runtime observability**, and anything requiring network at the deployment site.
  Out of scope for the same reasons as last time.

## 8. Section 4, decided

Added 2026-08-30, after §4 was worked through one item at a time (issue #21).
**§4 is left exactly as written** — it records what was believed on the survey
date, and rewriting it would destroy the evidence of what changed. This section
records what was decided and the measurement behind each decision.

T2 and T3 are not here: they are issues #6 and #20, and #20 has shipped. Of the
rest, two are adopted, one is built twice for comparison, and seven are declined.
Six of the seven were declined on a number this survey did not take, which is why
they are recorded rather than merely closed.

### 8.1 · Adopted

**T5a, four of the five optional shellcheck checks.** Measured over the two globs
`lint.sh` already covers, ~1160 lines: `check-unassigned-uppercase` 0,
`quote-safe-variables` 0, `avoid-nullary-conditions` 0,
`check-extra-masked-returns` 9, `require-variable-braces` 293. The first four are
on. `require-variable-braces` is out: all 293 are mechanical `$var` → `${var}`
with no correctness content, and that diff would have buried the nine.

Two of the nine were real defects. `lib.sh:135` tested
`[ -n "$(git ... status --porcelain ...)" ]`, where a failing git is
indistinguishable from a clean tree — `source_revision()` recorded a clean SHA
for a dirty one, the `image_tag()` shape again. `image-build.sh:43` passed
`BUILD_DATE="$(now_utc)"` inline, shipping an empty label rather than no label.
Both now assign on their own line where `set -e` sees the failure. The other
seven are `du`, `jq`, `basename` and `id` inside `log` and `die` strings and
carry `|| true`.

**Flags on the invocation, not a `.shellcheckrc`.** §4.5 assumed the config file.
A `.shellcheckrc` is searched for upward from each input and is silently ignored
when absent or when it names a check the running shellcheck does not know; an
unknown `-o` name exits non-zero. That difference is live — the EPEL shellcheck
here is 0.10.0 and `os-deps.sh:29` installs an older one from apt on
`ubuntu:24.04` — and `conftest.py:7` requires it to fail loudly.

**The two extra `run` blocks in `libvirt-module.tftest.hcl`** (§4.7). The gap was
larger than "two uncovered branches": `tests/golden/libvirt.tfvars.json` sets
`base_volume.create = true` and gives every NIC `network` with `bridge = null`,
so `main.tf:25`, `main.tf:34`'s fallback and `main.tf:205`'s non-null bridge arm
were evaluated by no test. The bridge arm is the shipped design —
`findings.md` settles the network as bridged, `config.py:16` accepts exactly one
of bridge/network — so the only tested path was the one a real RHEL 9 site does
not take. Both new blocks were proved to fail before being trusted, each by a
mutation that fails it and leaves the other two passing.

### 8.2 · Built twice, and not yet decided: T1

§4.1's recommendation splits into two jobs at two prices, and the survey's
half-day estimate belongs to the cheaper one. A stock Alpine qcow2 gives real
libvirtd, real `virStorageVolUpload` and real domain define/start/undefine — more
than any mock here — but the defect-5 class stays invisible, because catching a
guest that boots healthy on the wrong address needs a cloud-init-capable image, a
boot wait and an address assertion.

Both are therefore implemented on their own branches, `t1-smoke-reduced` and
`t1-smoke-full`, as draft PRs, so the comparison is made against two running jobs
rather than against an estimate.

**§4.1's mechanism does not exist, and this is the correction that matters most
in this section.** `TF_PROVIDER_LIBVIRT_DOMAIN_TYPE=qemu` is quoted there as the
thing that swaps `type='kvm'` for `type='qemu'` and so removes the `/dev/kvm`
requirement -- the load the whole recommendation rests on. Measured against the
mirrored `terraform-provider-libvirt_v0.9.8` binary: **zero** occurrences of
`TF_PROVIDER_LIBVIRT` or `DOMAIN_TYPE`, against a control showing the same binary
does carry `TF_LOG_PROVIDER`, `TF_PLUGIN_MAGIC_COOKIE` and
`TF_REATTACH_PROVIDERS`, so the search works. The variable belongs to the
provider's own Go acceptance-test suite, which is what `make testacc` runs in the
CI recipe §4.1 copied; the released provider never reads it.

It would not have sufficed regardless: `main.tf` sets `type = "kvm"` as a
declared attribute, and no environment-variable default overrides that. Reaching
TCG means overriding two attributes -- `type`, and `cpu`, because
`host-passthrough` renders as `-cpu host`, which defines cleanly and then fails to
start under TCG.

**And that is the fork the two branches actually took, on the same evidence.**
`t1-smoke-reduced` writes those two overrides into a *copy* of the module, so it
needs no `/dev/kvm` and stays portable -- at the cost of no longer asserting the
two values the module really ships. `t1-smoke-full` refuses to mutate the module
under test, on the ground that a patched module reports on the patch, and takes
`/dev/kvm` instead -- at the cost that it cannot run on GitLab.com SaaS under any
design, needing root, systemd and `NET_ADMIN` besides. §7 of this document already
warns that `/dev/kvm` on hosted runners is unconfirmed
(actions/runner-images#12933, still open) and says not to build a gate on it; it
calls that moot for §4.1, which was only true while TCG looked free.

**§4.1's proposed assertion is also too weak, and this was measured rather than
argued.** It says "a smoke test that boots a tiny image and asserts the address is
the only gate class that could" catch defect 5. `t1-smoke-full` injected defect 5
deliberately and the address assertion **passed**: libvirt's dnsmasq leased the
guest `192.168.122.60`, the configured address, so a gate asking only "does the
configured address answer" would have been green with the defect present. What
caught it was asserting that the guest took **no DHCP lease at all**. The
distinction is the gate.

### 8.3 · Declined, each with the measurement

**T4, `trivy fs` on `uv.lock`.** `Containerfile:118-124` installs all three
runtime dependencies as RPMs, so `trivy image` already covers them against a
reachability-assessed baseline, and nothing dev-side ships. Both placements §4.4
offers are also defective. In `image-scan.sh` the scan inherits the `image` job's
path filter (`image.yml:21-40`), which does not list `uv.lock` — the gate would
not run when its subject changed. In `check` it becomes a blocking gate driven by
third-party disclosure timing, with no equivalent of `cve-baseline.json`'s
per-finding `why` and `recheck`.

**T5b, shfmt — declined on provenance, before value.** v3.14.0 (2026-08-28)
publishes eight release assets, all raw binaries: no checksums file, no
signature, no provenance in the release body. `install-tools.sh:12-15` requires
every digest to come from the project's own published checksums file, refreshable
by fetching that file again rather than by trusting a download, and shfmt cannot
meet it. There is also no Rocky 10 or EPEL 10 package (checked against the
enabled repos), so vendoring was the only route. Secondary: it is the one item in
§4 with no defect behind it, it would be a seventh unautomatable pin, and the
normalisation pass across ten heavily-commented scripts was never measured. The
PyPI channel would carry a hash through `uv.lock` but substitutes a third-party
repackager for the missing upstream checksum, which is a worse trade for a style
gate, not a better one.

**T6, `--source-date-epoch` and `--rewrite-timestamp`.** The flags are present
(podman 5.8.2, re-confirmed). The justification is not. §4.6 argues they make the
monthly rebuild diff readable, but `scheduled.yml:68-73` states in its own words
that the job's comparison is this month's SBOM against last month's — and the
SBOM has no timestamps. Measured on the 7 MB `sbom.spdx.json` from a local run:
7961 file entries carrying `fileName`, `fileTypes`, SHA1/SHA256 and licence
fields; package entries carrying name, version, licence and `sourceInfo`; no
mtime anywhere. The only time-varying fields in the document are
`creationInfo.created` and the UUID in `documentNamespace`, two lines.

The indirect path fails too. Every file entry carries `comment: "layerID:
sha256:…"`, and layer digests do cover in-layer mtimes — but the digest changes
anyway on tar entry ordering, rpmdb ordering and dnf drift, which §4.6 itself
says the flag does not touch and which `lint.sh:139-147` already records as the
reason two builds of the same commit differ. Adopting it would remove timestamp
noise from a diff that has none, fail to stabilise the field that does churn, and
risk reading as a reproducibility claim this project has declined in writing.

**gitleaks.** History is clean, and verified rather than assumed: across all 97
commits on all refs, no key-material filename was ever added, no
`BEGIN … PRIVATE KEY` block appears in any ref, and the tracked tree carries no
credential assignments. Recorded for whoever revisits this: gitleaks *would* meet
the pinning contract — v8.30.1 publishes `gitleaks_8.30.1_checksums.txt` — there
is no Rocky 10 or EPEL 10 package, and the unmeasured cost is false positives
against the 514 distinct 64-character hex strings in `Containerfile`,
`install-tools.sh`, `uv.lock`, `licenses/dmacvicar-libvirt/PROVENANCE.md` and one
review evidence file. The trigger to revisit is credentials ceasing to be
cleartext, which `findings.md` calls explicitly temporary.

**`just cov` — the premise is wrong.** §4.7 says `--cov` appears in no recipe and
treats `pytest-cov` and `fail_under` as inert. `justfile:64-66` is `test *ARGS`,
commented "`just test -k name` and friends pass through", and `pyproject.toml:70`
sets `source = ["orchestrator"]`, so bare `--cov` needs no argument. Measured:
`just test --cov` reports `TOTAL … 96%`, then `Required test coverage of 90.0%
reached. Total coverage: 96.49%`. The floor is enforced and the number is
producible today. Only its spelling was undocumented.

**actionlint — declined on value, not provenance.** v1.7.12 publishes
`actionlint_1.7.12_checksums.txt`, so it could be pinned like the six existing
tools. Its principal feature has an empty surface here: 25 `run:` lines across
the three workflows, **zero** carrying shell logic, because `lint.sh:54` already
fullmatches them against `just [a-z][a-z-]*` and the two bootstrap scripts. Eight
`${{ }}` expressions, all `github.sha` or `hashFiles(...)` in cache keys and
artifact names. No `needs:` edges. And it does nothing for `.gitlab-ci.yml` — 166
lines, four jobs, never executed by its own header — which remains the larger
unvalidated surface, and is the finding actionlint points at without addressing.

**vulture — the gap is real and currently empty.** ruff's F401, F841 and ARG do
not catch unused top-level functions or classes, so §4.7 is right that nothing
covers it. Measured: 128 top-level `def`/`class` names across `orchestrator/` and
`container/`, **zero** with no reference beyond their own definition. Method and
its limits, so a recheck knows what was and was not covered: a name-reference
count over `orchestrator/`, `container/` and `tests/`, which does not see unused
attributes or class members. Provenance is trivial (PyPI, through `uv.lock`), so
this too is a value rejection — a dependency, a seventh `lint` gate paid on every
agent turn, and a whitelist tuned against the string-dispatched backend registry,
bought against a measured zero.
