# kcli as a replacement for vcows: measured 2026-09-02

Issue #197 asked whether kcli (karmab/kcli, Apache-2.0) covers what vcows does,
and named five measurements. This run took those five and six more on the rig
(`qemu+ssh://vcows@vcows/system`, pool `images`), from a venv on the dev box,
against kcli 99.0.202608310804 (upstream commit `48bf09af`, 2026-08-31). Every
number below came from a command in `/home/ssullivan/kcli-eval/evidence/`, and
nothing outside a `kclieval-` prefix was created or touched. Section 8 is the
end-of-run rig diff.

Assumptions given for this evaluation: the product stays a podman image
tarball, a basic web dashboard is likely, custom golden images are mandatory,
forking is acceptable, and the RPM-only dependency rule is relaxed to "RPM or
pip".

## 1. Verdict

**Borrow, do not adopt.** The never-adopt mismatch turned out cheap to patch
in a fork: +18/-3 lines closes it, and the patch passes the decoy test upstream
fails. Validation, address preflight, the boot gate, the golden-image upload
and Proxmox-by-token-only are each new code on top of the fork (section 4).
What does not close at any patch size is the ratio: kcli is 51,681 lines of Python carrying one 84-line test
file, and a fork would own all of it to use the ~4,000 lines (`config.py` plan
path plus the KVM provider) that vcows needs. vcows is 5,991 lines with 12,376
lines of tests. The deciding measurement is section 4 row "tests", not any
single feature gap.

What kcli does better, and is worth taking: the `<kvirt:info>` metadata block
is the same idea as the vcows marker and survives a rename the same way (M2);
`cloudinit_file` gives a verbatim user-data override alongside a generated
network-config, which is the split vcows already uses (M5); `kweb --readonly`
is a working, if unauthenticated, read-only dashboard over the same domain
metadata (M7) and is the cheapest answer to the dashboard assumption if the
answer is "run kcli's, read-only, next to vcows" rather than "fork kcli".

## 2. The five measurements from #197

| # | Question | Result |
|---|---|---|
| 1 | Dependencies, RPM path on Rocky 10 | `pip install kcli` **fails** on a box without `libvirt-devel` (pulls `libvirt-python` 12.7.0 sdist and compiles). With the RPM binding and `--no-deps`: 7 packages, 2.9 MB of wheels, all binary. Every core dep (`PyYAML jinja2 prettytable argcomplete python3-libvirt`) is in Rocky 10 appstream/baseos. kcli itself is pip or the `karmab/kcli` COPR (`epel-10` chroot exists). Official image `quay.io/karmab/kcli`: 934 MB. |
| 2 | Identity | Domain `<metadata>` carries `<kvirt:info xmlns:kvirt="kvirt">` with `creationdate plan profile image user ip`. After `virsh domrename`, `kcli list vm` and `kcli list plan` still show the domain under plan `kclieval`, and `delete plan` deletes it. **Its two volumes (`_0.img`, `.ISO`) leaked** after the rename: `Kvirt.delete` reads the disks from the XML but keeps only paths matching `{name}.ISO`, `{name}.img` or `{name}_`. |
| 3 | Adoption | `create plan` naming an unmarked domain prints `skipped` and exits 0. `kcli delete vm <unmarked>` **deletes it with no ownership check**. Plan-level operations are scoped by metadata: `delete plan kclieval2` and `create plan kclieval2 --force` did not touch plan `kclieval`'s VM. |
| 4 | Convergence | Re-running `create plan` with a changed `memory:` skips. `update plan` edits the persistent XML (3 GiB on next start, no reboot, exit 0). Never-converge holds only if `update plan` is never run. |
| 5 | Air-gap install | Rocky 10 image built from RPMs plus `pip install --no-deps` of the fork checkout: see section 5. |

## 3. Six more, for the assumptions given

- **M5 custom golden image.** `vcows-acceptance-golden.qcow2`, already a pool
  volume, is used as-is by name (no download), the VM disk is a COW overlay on
  it, the seed ISO goes over the libvirt stream. Static `.91` applied, SSH in
  27 s (stock Rocky 9 image: 15 s), `cloud-init status: done`. Raw user-data:
  `cloudinit_file: <path>` in the profile (or `<name>.cloudinit` in cwd)
  replaces the generated user-data verbatim; network-config is still generated.
  Defaults in the generated user-data that vcows does not set: `ssh_pwauth:
  true`, `disable_root: false`, `lock_passwd: false`, and the file fails
  cloud-init schema validation (`ssh-authorized-keys`, `gateway4`).
- **M6 golden image from the deploy box.** There is no push path. `add_image`
  in the KVM provider runs `ssh host "curl -Lko <url>"` so the hypervisor
  fetches a URL into the pool directory; a plan with `image: /local/path` fails
  (`you don't have image`, exit 1). On this rig the pool directory is
  `root:root 711`, so `download image` as `vcows` would also fail without
  `setfacl`. vcows covers this with `libvirt_volume.base` uploaded over the
  connection; kcli has nothing equivalent short of `virsh vol-upload` by hand.
- **M7 dashboard.** `kweb` is Bottle (vendored, 4,573 lines) plus jinja2. 98
  routes, HTML tables and a JSON API. `--readonly` is the only flag; port 8000
  and bind address `::` are fixed; `--readonly` returns `403 {}` on `DELETE
  /vms/<name>`; there is no authentication (`auth` appears twice in the file,
  both kubeconfig paths). Read-only mode lists foreign domains too.
- **M8 offline validation.** None. `kcli render` prints the plan through jinja.
  `create plan` with an unknown key (`numcpuz`) and `ip: 192.168.122.999`
  deployed the VM and wrote `.999` into `<kvirt:ip>`. No dry-run flag; the
  `create plan` flags are `-P --paramfile -A -u -p -c --force -f -t`.
- **M9 destroy.** `delete plan` removed the overlay and the ISO and left the
  base volume's mtime unchanged. `delete vm` also removes volumes.
- **M10 side effects.** After all runs: `~/.ssh/known_hosts`, `~/.ssh/config`
  and `/etc/hosts` unchanged; only `~/.kcli/config.yml` and `~/.kcli/vm`
  written. `kcli version` calls `api.github.com` for an update check. 42
  `shell=True` call sites across `config.py`, the KVM provider and
  `common/__init__.py`, with the image URL interpolated into one of them.
  `delete plan` prompts unless `-y`.
- **M11 Proxmox, desk only.** Provider is 1,165 lines, token auth
  (`token_name`/`token_secret`) supported. Metadata is a `key=value` list in
  the VM description (vcows: one `vcows:` JSON line, same place). `filtertag`
  filters `list` by a PVE tag; `delete` has no ownership check. Image download
  and cloud-init snippet upload go over `ssh root@<node>` and `scp`, so a token
  alone is not enough; vcows's backend needs only the token.

## 4. Fit matrix

| vcows property | kcli | Fork closes it |
|---|---|---|
| Identity in domain metadata, survives rename | yes (`<kvirt:info>`) | n/a |
| Never adopt: refuse unmarked or foreign name clash | no: skip + `delete vm` deletes | yes, +18/-3, measured |
| Never converge | yes for `create plan`; `update plan` converges | remove or gate `update plan` |
| Destroy re-verifies marker | `delete plan` yes, `delete vm` no | in the +18/-3 |
| Orphan volumes on rename | leaks | not attempted |
| Whole-batch offline validation (`validate`) | none | new code, kcli has no schema |
| Address-conflict preflight | none | new code |
| Boot gate reading the guest | none (a `wait` exists) | new code |
| Custom golden image staged in the pool | yes, by name, COW overlay | n/a |
| Golden image uploaded from the deploy box | no (`ssh curl` pull only) | new code |
| Verbatim `user_data` | yes (`cloudinit_file`) | n/a |
| Seed ISO without host tools | yes (libvirt stream) | n/a |
| Machine type | `pc-i440fx` default | one keyword |
| Podman image from RPMs, no pip at runtime | yes, section 5 | n/a |
| Dashboard | `kweb --readonly`, no auth | auth is new code |
| Proxmox with token only | no, needs `ssh root@node` | new code |
| Tests | 1 file, 84 lines | all of it |

## 5. Delivery shape

`/home/ssullivan/kcli-eval/Containerfile`: `quay.io/rockylinux/rockylinux:10`,
`dnf install` of the RPM deps plus `openssh-clients xorriso nmap-ncat` (no
EPEL), then `pip install --no-deps` of the fork checkout with pip installed
and removed in the same layer. No pip, no setuptools in the final image; 164
RPMs; `import kvirt, libvirt` works. Build needs the network for pip's
build-isolation venv (Rocky 10's RPM setuptools has no `bdist_wheel`, and
`python3-wheel` is CRB/EPEL only); runtime does not.

| image | `podman images` | `podman save \| gzip -9 -n` |
|---|---|---|
| `localhost/kcli-eval:spike` | 357 MB | 117,447,554 B |
| `localhost/vcows-deploy:0.1.0.0` | 486 MB | 171,513,687 B |
| `quay.io/karmab/kcli` | 934 MB | not measured |

The 130 MB difference is OpenTofu and the two providers. That is what #198
is about, and it is the whole of the size argument.

Offline shape: `--network=none kcli render` exits 1 with `No configuration
found nor local hypervisor` when `~/.kcli/config.yml` is absent, because
`kvirt.cli` builds a `Kconfig` before dispatching any subcommand; with the
config mounted it renders. `list vm` fails with the same message, so kcli does
not distinguish "no config" from "no socket".

On the rig, from the container with `--net host`, `~/.kcli` and `~/.ssh`
mounted read-only: `create plan` deployed `kclieval-a` and `delete plan`
removed it, both exit 0. Two things had to be worked around. The host
`~/.ssh/config` names the key by absolute path, so `~/.ssh` had to be mounted
at both `/root/.ssh` and its host path before ssh could authenticate; vcows's
`entrypoint.py::ssh_config` exists for this. And `delete plan` ran `sed -i` on
`~/.kcli/vm` (a "last VM" convenience file) and printed a read-only error
before succeeding: kcli keeps local state under `~/.kcli`, including
`vmclients_<plan>` per multi-client plan.

## 6. Fork cost

Branch `vcows-guards` in `/home/ssullivan/kcli-eval/kcli`, commit `8293bad3`:

```
kvirt/config.py                  |  5 +
kvirt/providers/kvm/__init__.py  | 16 +-
2 files changed, 18 insertions(+), 3 deletions(-)
```

G1 adds a `plan=None` keyword to `Kvirt.delete` and refuses when
`<kvirt:info>` is absent or the plan differs. G2 refuses in `Kconfig.plan`
when an existing same-name domain is not owned by the plan being created, and
records it in `failedvms` so the exit code is 1. G3 (passing `plan=` from
`delete_plan`) was not done: all 13 providers share the `delete(name,
snapshots)` signature and the keyword would `TypeError` on twelve of them.

Re-running the M3 decoy test on the fork: create refuses (exit 1), `delete vm`
refuses, the decoy survives, cross-plan create refuses, same-plan re-run still
skips, owned `delete vm` still works. Evidence in `evidence/M3-fork/`.

Standing cost of the fork, not measurable tonight: upstream is one author (140
of 169 commits in the last 12 months), versions are `99.0.<timestamp>` with
195 PyPI releases in 12 months and no changelog, and the two files the guards
live in are 3,489 and 4,351 lines. Each rebase re-reads both.

## 7. What to take from this

1. Nothing structural in the marker design is wrong: kcli reached the same
   answer, and rename survival works the same way on both.
2. `kweb --readonly` next to vcows is the cheapest dashboard test. It reads
   `<kvirt:info>`, not `<vcows>`, so it would show vcows VMs without a plan;
   teaching it the vcows namespace is a small patch in `Kvirt.list`/`info`.
   Whether that is smaller than a read-only page over `inventory.json` is the
   next measurement, not this one.
3. The volume leak on rename (M2) is a defect vcows should test for on its own
   destroy path: `libvirt/destroy.py` takes disks from the re-read XML
   (`disks_of(root)`) rather than from the name, which is the right side of
   that line. `tests/test_policy.py` covers rename for `decide`; nothing
   renames before `destroy`, and one rig test would pin it.
4. `#198` gets one input: OpenTofu's create path is what gives vcows the
   golden-image upload kcli lacks (M6). Dropping tofu means writing that upload
   in Python (`virStorageVol.upload` over the stream, which kcli already does
   for the ISO).
