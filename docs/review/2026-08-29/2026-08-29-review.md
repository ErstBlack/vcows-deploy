# vcows-deploy v0.1.0.0 — code review

Reviewed 2026-08-29, `45d5b92`..`da3f45c` (eleven commits), by nineteen agents plus
this orchestrator. Per-agent detail is in `docs/review/2026-08-29/NN-*.md`; this
document is what a maintainer acts on. Nothing was modified.

## 1. Verdict

**This is shippable to another team as v0.1 once section 2's first two items are
fixed, and it is closer to ready than a codebase this young usually is** — 44 of 52
decisions held, no decision was silently reversed, and the acceptance run's five
defects were all genuinely closed. The one thing that would stop me is
**F-SEC-01**: a newline in `ssh_keyfile` or `known_hosts` injects arbitrary OpenSSH
directives, which is remote command execution as the user holding the private key,
in a tool whose own design document says other groups author these configs by hand.
Everything else in section 2 is a real defect with a cheap fix, and the pattern
underneath most of them is one thing — vcows computes an outcome and then does not
report it.

## 2. Act before anyone else depends on this

Confirmed by `17-verify-severe` and re-verified against source by me. Ordered by
severity, then by cheapness of fix.

### S1 — 2 findings

**2.1 · `ssh_keyfile` / `known_hosts` inject OpenSSH directives** — S1
`backends/libvirt/schema.py:103-104`, `container/entrypoint.py:75-79`
· *18-security-adversary F-SEC-01, verified 17*

Both fields are `{"type": "string", "minLength": 1}` with no pattern, and
`ssh_config()` interpolates them line-wise into `~/.ssh/config`. A newline injects
`ProxyCommand` — executed through `/bin/sh -c` on every ssh invocation — and an
injected `StrictHostKeyChecking no` beats the tool's own `yes`, because OpenSSH
takes the first value obtained. 17 confirmed both against real OpenSSH 9.9p1:
`ssh -G` returns `stricthostkeychecking false` and
`proxycommand /bin/sh -c 'id>/tmp/pwned'`. This reopens precisely the hole that
`_check_target`'s query-string refusal exists to close — the check `schema.py:222`
calls the most important one it makes. Two aggravators: `install()` runs on
`validate` too, so `vcows validate` writes the poisoned file while claiming nothing
is written; and it returns early when `~/.ssh/config` exists, so one hostile config
poisons every later clean run.

**Fix:** a path pattern on both fields — `^/[^\s]*$` matches how they are actually
used. **Cost:** two regex strings in an existing schema dict. No new surface, and
the justification is already written for the query string.

**2.2 · destroy acts on a stale snapshot across an unbounded confirmation prompt** — S1
`cli.py:258-294` acting through `destroy.py:243-255`
· *16-warning-severity F-WARN-02, adjudicated by 17*

`cmd_destroy` collects `targets` — names, UUIDs, disk paths — from one preflight
walk, blocks on `input()` with no timeout, then tears down from that snapshot.
I verified there is no re-read of any kind between the prompt and
`backend.destroy(...)`, and that `destroy.py` contains **no `XMLDesc` call at all**.
Domain UUIDs are libvirt-assigned while overlay and seed paths are deterministic
from the logical name, so a deployment destroyed and redeployed during the pause
gives a UUID that no longer resolves, the "already gone" branch, and deletion of the
**new running VM's** overlay and seed ISO — `destroyed 1 VM(s)`, exit 0.

17 corrected 16 on one point that matters for the fix: the stale UUID misses with
`ERR_NO_DOMAIN` (42), so this fires on the *correct* branch and is **not** closed by
narrowing the bare catch (2.9). The two fixes are independent, and shipping one
while believing both are closed is the trap.

**Severity is my call, and I am keeping it at S1.** The consequence is silent data
loss on a running guest; the weak leg is frequency, which needs a concurrent
destroy-and-redeploy while a prompt sits open. I weight it S1 anyway because the
tool is explicitly built for hypervisors shared between deployments — that is why
`deployment` is in the marker at all — and because the fix is ~12 lines.

**Fix:** after `_confirm` returns true, re-read each target's `XMLDesc` and drop any
whose UUID no longer resolves or whose marker no longer matches. **Cost:** one loop
reusing `marker_of` and `disks_of`, one extra `XMLDesc` per target. It reduces the
window to findings.md §2's already-accepted TOCTOU.

### S2 — 13 findings

**2.3 · `destroy()` discards its own `Outcome`; leaked disks report success** — S2
`destroy.py:233-258`, `cli.py:294-304`
· *four agents: 02 F-LVC-01, 08 F-SILENT-02, 11 F-LIFE-01, 16 F-WARN-01*

Verified: `destroy` is `-> None` at all three layers, `cli.py:294` calls it as a
statement, and `_record` writes `sorted(e.name for e in targets)` — intent, never
result. `_refresh_pools` skips an inactive pool with a bare `continue`, so every
disk in it reads as "already gone", the domain is destroyed and undefined (marker
gone), both volumes stay on disk, and the operator is told the teardown succeeded.
16 reproduced this end to end through `cli.main`. This is the defect the file's own
docstring says it exists to prevent.

**This is the highest-leverage fix in the review**: it is the root of four filings
and it makes three false docstrings true at no extra cost.

**Fix:** return the `Outcome`, print `skipped` and every non-fatal `Problem`, pass
both into `_record`, and make a non-empty `skipped` non-zero. **Cost:** one return
type on `Backend.destroy`, ~8 lines in `cmd_destroy`, two `run.json` keys.

**2.4 · D30's size-mismatch remedy tells the operator to delete every VM's backing file** — S2
`backends/libvirt/preflight.py:300-309`
· *three agents: 02 F-LVC-02, 11 F-LIFE-02, 15 F-XDEP-01*

I read the message. It says "…either way every overlay would back onto it. **Delete
it on the hypervisor and re-run.**" — it states the shared-backing fact in the clause
before instructing against it. `virsh vol-delete` has no backing-chain awareness, so
an operator who follows it unlinks the backing file of every overlay on that host
across every deployment; running guests survive on open descriptors and fail at
their next boot. The trigger is the intended workflow, not corruption: a refreshed
golden image is a different size, so this fires *every time* under the README's
`base_volume_name: golden.qcow2`.

17 held this at S2 rather than 15's S1 on the grounds that the tool refuses and
changes nothing — a human must act. I agree, and note it is the cheapest
high-consequence fix here.

**Fix:** name the non-destructive procedure, which already works — a new
`base_volume_name` sets `create = True` and uploads alongside. 15 adds that `walk()`
already holds the `<backingStore><path>` data needed to say how many overlays would
break. **Cost:** two sentences in one f-string, plus one `findtext` and a counter.

**2.5 · No run record survives any failure path** — S2
`cli.py:173-233`, `:254-305`, `:393-399`
· *four agents: 05 F-DRV-03, 11 F-LIFE-04, 13 F-RUNDIR-01, 16 F-WARN-03*

`_record` is reached only on the five non-exception outcomes. A failed apply writes
`seed/` and `tofu/` but no `run.json` and no `inventory.json`; a failed or
interrupted **destroy** leaves the directory completely empty. The run directory is
what an air-gapped site ships back for support, and it is present for every run
where nothing happened and absent for every run where something did — acceptance
defect 3 was exactly this shape. `outcome` has no `failed` value.

**Fix:** wrap each verb's body from `_run_dir` onward in `try/except BaseException`,
record `outcome="failed"` with the exception text, re-raise. **Cost:** one
try/except/raise per verb and one new `outcome` string; the re-raise leaves §3's ban
on a shared exception hierarchy untouched. Must wrap `cmd_destroy`, not only
`cmd_deploy`.

**2.6 · The README's own `--run-dir` invocation crashes the second deploy** — S2
`cli.py:71-81` (`exist_ok=True`) vs `:203`, `:205` (no `exist_ok`)
· *05 F-DRV-01, 13 F-RUNDIR-03*

Verified in source. `deploy /config.yaml --run-dir /runs/lab-a` is the only worked
example README gives; the second run dies with a bare `FileExistsError` naming
neither `--run-dir` nor a remedy — *after* the connected preflight has run and
printed clean. The destroy face is worse in kind: destroy creates no subdirectories,
so it reuses silently and overwrites the earlier deploy's `run.json` while leaving
its `inventory.json` beside it, producing a directory that is internally coherent
and wrong.

**Note for the fixer:** agents 04 and 08 both listed this mechanism under "checked
and sound" as a construction guarantee (D23/D40). It is both — it does prevent a
re-apply against non-empty state, and it breaks the documented workflow. Fix the
ergonomics without losing the guarantee.

**Fix:** refuse a *non-empty* `--run-dir` in `_run_dir`, before `_look()` spends a
connection; an empty one still works for a bind-mounted mountpoint. **Cost:** one
conditional and one message; both verbs inherit it.

**2.7 · `main.tf` is pinned by no behavioural test; every module mutation survives** — S2
`backends/libvirt/tofu/main.tf`, `tests/test_tofu_module.py`
· *12-test-teeth F-TEETH-01, reproduced independently by 17*

`tofu validate` and `tofu console` check types, never attribute *values*. 12 ran
twelve `main.tf` mutations and all twelve passed the full suite; 17 re-ran six,
including acceptance defects 1, 3 and 4 re-introduced verbatim, each giving
`218 passed, 25 skipped`. Deleting `metadata = { xml = … }` — the tool's only
identity — produces VMs that boot correctly, report success, and can never be torn
down by `vcows destroy`. Three of the five acceptance defects lived in this file and
none of the three fixes is pinned.

17 moved this from S1 to S2: it is a gap admitting an S1 rather than a live one.

**Fix:** `tofu console` already loads the golden tfvars into the initialised module,
so evaluate and assert `metadata.xml`, seed `format`, `backing_store`, overlay
`capacity`, `features`, `nv_ram`, `boot_devices`, `running`. **Cost:** ~60 lines
inside the existing `needs_tofu` gate, no runtime surface.

**2.8 · The shipped image records a commit it does not contain** — S2
`container/manifest.py`, `tests/test_image.py:241`
· *19-completeness-critic G2; verified by me*

I confirmed this directly. The image's `/opt/vcows/manifest.json` reports
`git_sha: e5d5a2c…`, and `git cat-file -e e5d5a2c:container/entrypoint.py` returns
**absent** — yet the image ships that file. HEAD is `da3f45c`. The build ran from a
dirty tree, and R5's whole purpose is answering which build produced a given
artifact. `test_the_build_manifest_records_what_shipped` asserts six manifest keys
and not `git_sha`. This is also a licensing record, which raises the cost of it
being wrong.

**Fix:** two asserts in that existing test — `git_sha` is 40 hex and equals
`git rev-parse HEAD` when `git status --porcelain` is empty — plus a build-time
guard recording a `-dirty` suffix rather than a clean SHA. **Cost:** two asserts and
one shell conditional.

**2.9 · The one bare `libvirtError` catch in `destroy.py` deletes disks for a domain it never resolved** — S2
`destroy.py:243-246` falling through to `:254-255`
· *08 F-SILENT-01 → 14 F-DSK-01 → 17*

I read it: the `for path in target.disks` loop sits **outside** the `try/else`, so it
runs on the "already gone" branch. 14 reproduced deletion under eight injected error
codes with the domain still running. Its severity travelled: 08 filed S1, 14 refuted
to S3 for want of a reachable trigger (the realistic codes kill the storage driver
two lines later, which is fatal and loud), and 17 confirmed 14. I am filing it S2
rather than 14's S3 because the fix is one constant and one `if`, and because 2.2
shows the same branch reachable by another route — but the *harm* here is bounded to
one VM's own overlay and seed. 14 established that no vcows domain can carry the
golden base in `target.disks`.

**Fix:** add `ERR_NO_DOMAIN = 42` beside the three existing constants, pin it in
`test_error_codes_match_the_installed_binding`, and make any other code a fatal
`Problem` that skips the disk loop. **Cost:** one constant, one `if`, one assertion.

**2.10 · `derive_mac` and `derive_id` ignore `deployment` — a one-way door, open now** — S2
`backends/libvirt/schema.py:122`, `marker.py:derive_id`
· *03 F-LVOFF-02, 15 F-XDEP-03*

`uuid5(VCOWS_NS, f"{name}#nic{index}")` takes no deployment and no host, so two
deployments each containing `app01` derive the identical MAC and instance-id;
`address_conflicts` only ever looks at one host. On two hosts bridged to one L2 both
guests boot, apply their static addresses, and report `cloud-init status: done` on
one MAC. The `network:` form in the README is per-host NAT and immune; `bridge:` is
not.

**This is the item with a deadline.** `derive_mac`'s own docstring says the
derivation is permanent, and nothing has shipped, so it is free today and impossible
later. Settle it together with 2.11 and with whether volume names get decorated.

**Fix:** fold `deployment` into the uuid5 input. **Cost:** one f-string and two
re-pinned tests.

**2.11 · The orphan-volume refusal names the wrong deployment and asserts one cause** — S2
`preflight.py:315-341`
· *15 F-XDEP-02, with 11 F-LIFE-01 supplying the second trigger*

Volume names are undecorated logical names in one flat pool, and `orphan_volumes`
reports with `where=vm["name"]` and the fixed text "A previous create was
interrupted; delete it on the hypervisor and re-run." So `lab-b`'s deploy can be
refused, blamed on `lab-b`'s VM, given a wrong cause, and told to delete `lab-a`'s
data. The second trigger is 2.3: a volume silently leaked by an incomplete destroy
resurfaces weeks later misattributed to an interrupted *create*, on the wrong verb.

**Fix:** state the cause as a possibility and say the volume may belong to another
deployment on this shared pool, because vcows cannot tell. **Cost:** one f-string.

**2.12 · `source_qcow2` is validated as a path and consumed as a URL** — S2
`config.py:42`, `schema.py:403`, `tofu/main.tf:30`
· *06 F-SUPPLY-02, 18 F-SEC-02, confirmed offline by 17*

Verified the schema is a bare string with no pattern. A value the local layer cannot
`open()` degrades to a WARNING rather than an error, so `file:///run/secrets/id_ed25519`
skips the `NotAQcow2` gate and reaches `create.content.url`, which the pinned
provider schema documents as "URL to download content from". As a security property
that is a config author reading any file the container's UID can and uploading it
into the hypervisor's pool; as an air-gap property it is the one runtime egress path
the removed `direct` block does not cover.

**Unverified half:** whether the provider actually resolves `file://` / `http://`
there needs one rig execution nobody performed. The fix does not depend on the
answer.

**Fix:** `"pattern": "^/"` on `source_qcow2`. **Cost:** one regex; the README's
contract is already a bind-mounted image at an absolute path.

**2.13 · A password in the URI validates, cannot work, and is written to disk twice** — S2
`schema.py:193-237`
· *03 F-LVOFF-01, 13 F-RUNDIR-04, 18 F-SEC-04*

`_check_target` inspects scheme, hostname, path, query and fragment — never the
userinfo — and `connection_uri` preserves the whole netloc, so the password reaches
`main.auto.tfvars.json` and `plan.bin` verbatim, in files that are 0644 and kept by
design. Neither client does password auth over these transports, so the operator
sees `Permission denied (publickey)` with no sign that what they typed is now on
disk. **13 corrected 03 and findings.md's F12 here:** it does *not* reach the
OpenTofu state, because provider configuration is not persisted.

**Fix:** reject a set `parts.password`, beside the four identical clauses already
there. **Cost:** six lines. The username stays.

**2.14 · `preflight`'s transport is asserted nowhere** — S2
`preflight.py:61`, `tests/test_libvirt_schema.py:293`
· *12 F-TEETH-02*

`connection_uri` is tested in isolation and `render`'s call site is pinned twice;
`preflight`'s is not pinned at all, so changing line 61 to pass `sshcmd` passes the
whole suite. That is half of acceptance defect 1 able to return unnoticed, presenting
at a site as `remote_open: transport in URL not recognised`.

**Fix:** monkeypatch `libvirt.open` in `test_libvirt_preflight.py` and assert the URI
scheme. **Cost:** ~6 lines, in a file that already fakes libvirt.

**2.15 · `<os firmware='efi'>` is emitted alongside a pinned loader and NVRAM** — S2, **NEEDS-EVIDENCE**
`tofu/main.tf:109`
· *04 F-TOFU-01*

I verified the code fact: the ternary is unconditional and does not consider whether
`loader` is set. These are two alternative mechanisms — with `firmware` set, libvirt
runs autoselection and fills loader and nvram itself. On Fedora 44 the pin was
honoured (acceptance A2); on the older libvirt Rocky/RHEL 9 ships it may not be, and
RHEL 9 is exactly the case the pin exists for.

**This is the one claim in the review that reading cannot settle, and it should not
be fixed on reading alone.** It needs a Rocky 9 host: define the module's XML for one
pinned-loader VM, `virsh dumpxml`, diff against the tfvars. If old libvirt honours
the pin, this drops to S5. The proposed fix is one expression —
`firmware = each.value.loader == null && … ? "efi" : null`.

## 3. Worth fixing

S3 and the S4 sprawl, grouped, one line each. Detail in the cited file.

**Ownership and the decide() seam**
- `by_logical` is a dict comprehension, so two domains claiming one logical name collapse and the verdict depends on libvirt's enumeration order — `base.py:173` (01 F-CORE-01, 10 F-SEAM-02).
- The name-clash refusal indexes only *unmarked* VMs, so a marked renamed domain yields CREATE onto a name that exists, failing inside `apply` after its volumes are written — `base.py:176` (01 F-CORE-02).
- `Marker.from_json` coerces wrong-typed fields with `str()` instead of raising, routing around D12's safe direction — `marker.py:125` (01 F-CORE-04).
- The unmarked-name-clash rule assumes hypervisor name == logical name, so it silently stops firing off libvirt — `base.py:163` (10 F-SEAM-01).

**The connected half**
- `preflight` infers "does not exist" from *any* `libvirtError` on three paths, one of them a bare `pass` that degrades the address-collision check to reservations-only — `preflight.py:189`, `:359`, `:376` (02 F-LVC-05, 08 F-SILENT-04).
- A domain vanishing mid-enumeration aborts the whole preflight, and so blocks deploy and destroy — `preflight.py:129` (02 F-LVC-04).
- An uncaught `libvirtError` aborts the destroy loop mid-teardown, losing the accumulated `Outcome` — `destroy.py:103`, `:110` (02 F-LVC-03).
- A failed `pool.refresh(0)` is a WARNING and deploy proceeds on exactly the stale cache D35 exists to prevent — `preflight.py:210` (02 F-LVC-07).
- The orphan refusal is keyed on basenames host-wide, so an unrelated domain's `app01.qcow2` marks ours as claimed — `preflight.py:444` (02 F-LVC-06).
- `orphan_volumes` iterates `cfg["vms"]` only, so a volume orphaned for a since-removed VM is never reported and never destroyable — `preflight.py:328` (04, 15 F-XDEP-05).
- A volume whose XML will not parse vanishes from preflight with no `Problem` at all — `preflight.py:235` (08 F-SILENT-06).
- `destroy` deletes whatever `<source file>` the hypervisor's XML declares, filtered only on device type — the `<backingStore>` exclusion excludes an element, not a path — `preflight.py:87` (18 F-SEC-03).

**The offline half**
- `$` in the name and MAC patterns accepts a trailing newline; `config.py`'s patterns including `image.sha256` share it — `schema.py:37,39` (03 F-LVOFF-04).
- Every NIC carries a default route, so a two-NIC VM always gets two and NM's tie-break decides egress — `prepare.py:196` (03 F-LVOFF-03).
- `loader` is accepted without `loader_format`, declaring a qcow2 firmware as raw: the domain defines, starts, never boots — `schema.py:258` (03 F-LVOFF-05).
- No upper bound on `vcpus`, `memory_mib`, `disk_gb`; a maximum omitted on a one-way door can never be added — `schema.py:73-75` (03 F-LVOFF-06).
- An `ip_cidr` that is its own network or broadcast address validates — `schema.py:332` (03 F-LVOFF-08).
- `dhcp6: false` is inert under cloud-init's NetworkManager renderer, the RHEL 9.4+/10 path — `prepare.py:193` (03 F-LVOFF-07).
- `base_volume_name` is never compared against the derived volume names, and a collision produces 2.4's destructive advice — `config.py:47` (03 F-LVOFF-09, 04 F-TOFU-02).
- Nothing checks that `ssh_keyfile` and `known_hosts` exist, though the container could — `schema.py:103` (03 F-LVOFF-10).

**The module**
- No `autostart`, and no record that this was a choice: after a host reboot every VM stays down and a re-run prints `nothing to create`, exit 0 — `main.tf:84` (04 F-TOFU-03).
- No `discard = "unmap"`, so a 40 GiB overlay only ever grows, in someone else's pool, with no prune — `main.tf:151` (04 F-TOFU-04).
- `<rng>` and the clock timers are the only devices libvirt does not default and neither choice is written down — `main.tf:149` (04 F-TOFU-05).
- **S4:** `output "base_volume_path"` has no reader — `outputs.tf:31` (04 F-TOFU-06).

**Driver, CLI and reporting**
- Ctrl-C SIGKILLs tofu 0.25 s in, so a mid-upload interrupt leaves a truncated base volume the next deploy refuses on — contradicting both D42 and the comment above it — `tofu.py:157` (05 F-DRV-02).
- `run.json` records decisions but never `problems`, so a refusal's reason exists only on stderr — `cli.py:94` (05 F-DRV-04).
- Nothing bounds a wedged SSH tunnel: no timeout by design (D42, correctly) and no `ServerAliveInterval` in the generated ssh config either — `tofu.py:35`, `entrypoint.py` (05 F-DRV-05).
- "Plan proposes no creates" also fires on an unreadable JSON stream, blaming the config for a full `/runs` — `cli.py:214` (05 F-DRV-07).
- `config.load` computes config WARNINGs on every verb and drops them; only `validate` recovers them by re-running — `config.py:132` (01 F-CORE-03, 16 F-WARN-04).
- A renamed module output yields `created 0 VM(s)` with `outcome: ok`, so a run's two artifacts contradict each other — `backends/libvirt/__init__.py:91` (08 F-SILENT-03).
- `inventory.json` states an address the tool never observed — the reporting property that let acceptance defect 5 pass, still in place — `outputs.tf:17` (08 F-SILENT-05).

## 4. Documentation drift

## 7. Themes

**7.1 · The tool computes an outcome and does not report it.** This is the largest
pattern in the review and it accounts for 2.3, 2.5, 2.11, most of section 3's
reporting bullets, and three false docstrings. `Outcome`, `Discovered.problems`,
`Result.diagnostics` and `ConfigError.problems` are four independently-invented
result carriers and three lose data at their consumer. The architecture rejected
`tofu destroy` specifically because it exits 0 on partial success; the Python path
reimplements that at the CLI boundary. Fixing 2.3 alone repairs four filings.

**7.2 · The acceptance run's shape recurs: emitted, accepted, not honoured.** Three
of five acceptance defects were a document a consumer took and did not act on.
Agents found four more instances: `dhcp6: false` inert under the NetworkManager
renderer; `<os firmware='efi'>` beside a pinned loader; a second default route
decided by NM's tie-break; and `inventory.json` asserting an address the tool never
observed — the reporting property that let defect 5 pass, still in place. The
netplan idiom is fixed; the class is not.

**7.3 · The marker carries `deployment`; nothing else does.** Every other derived
name — domain, overlay, seed, MAC, instance-id, NVRAM path — is keyed on the logical
name alone. `deployment` is enforced exactly where a marker can be read and nowhere
else, while findings.md:119 explicitly rejected "one deployment per hypervisor" as
an assumption. The consequences are 2.10, 2.11, the flat-namespace table in 15, and
the NVRAM varstore nothing can see. MAC and instance-id are one-way doors and are
free to fix only until first ship.

**7.4 · Where a check exists, it is good; the gaps are where nobody looked.** The
`<backingStore>` exclusion survived every construction three agents could build. The
NVRAM floor cannot be shed. `decide()`'s rules are right for every world it can see.
`qcow2.virtual_size` survived every malformed input. The seed ISO is correct through
both Rock Ridge and Joliet, byte-for-byte. Schema composition holds. `decide()` is
the best-tested code here. The defects cluster in the seams between components —
what the CLI does with what the backend returns, what the module emits that libvirt
must supply, what the entrypoint writes before validation runs.

## 8. Methodology

Nineteen agents, four phases, no failures and no retries. Agents 01–08 broad
coverage; 09–12 depth; 13–16 derived from phase A's convergence; 17–19 adversarial.
All ran on Opus. Per-agent files are capped at 200 lines (16 came in at 206).

**Derived agents and what prompted each**
- **13-run-dir-artifact** — five phase-A agents pointed at the run directory from different angles; 05 noted four of its own eight findings were that one shape.
- **14-destroy-disk-safety** — 02 and 08 reached opposite conclusions about `destroy.py`'s error handling. Commissioned to settle it, and it did, by refuting the agent that had filed the higher severity.
- **15-cross-deployment-collision** — 01, 02, 03, 04 and 11 each hit theme 7.3 from a different direction.
- **16-warning-severity** — 01, 02, 05 and 08 each found a signal computed and not printed.

**Outside influence, recorded for honesty:** a peer Claude session proposed its own
four-agent phase-B roster mid-run, numbered so as to overwrite three agents already
in flight. I declined the duplicate launches and folded its leads — which were more
specific than mine — into slots 15 and 16.

**The adjudication that mattered most** ran across four agents and is worth keeping
as a record of why the adversarial phase earns its cost: 08 filed an S1; 14 was
commissioned to settle it and refuted the severity with reproductions; 16
independently found a trigger and re-raised it; 17 then showed 16's trigger fires on
a *different* branch, splitting one disputed finding into two real defects with
independent fixes (2.2 and 2.9). No single agent reached that conclusion.

**Verified personally in phase D:** the destroy disk-loop's position outside the
`try/else`; the `FLOOR` constant; the absence of any `XMLDesc` in `destroy.py`; the
D30 message text; `cmd_destroy`'s control flow and `destroy`'s `-> None` signature at
all three layers; the ssh-config interpolation and both schema fields; the `main.tf`
firmware ternary; `_run_dir` versus `seed.mkdir()`; that `MANIFEST` is read only by
`cmd_version`; and that `container/entrypoint.py` is absent from the commit the
shipped image names.
