# OpenTofu's role, measured 2026-09-02: a direct create on two backends

Issue #198 lists three options for OpenTofu and says option 3 (drop it) is
worth taking only "if option 2 shows the SDK create path is as small as
predicted on two backends". The prediction was 150 to 200 lines per backend,
from a 2026-08-28 review whose text survives nowhere in this repository or its
issues; #198's summary of it is the only record. This run replaces the
prediction with two scripts and eight measurements.

The scripts were `docs/spikes/b1_libvirt_create.py` and
`docs/spikes/b2_proxmox_create.py`, deleted when the ports landed in
`orchestrator/backends/*/create.py` and still in history at 220827a. Each runs
the shipped code up to `render` exactly as `cli._deploy` orders it, then
consumes the dict `render` hands
OpenTofu and creates the VMs through libvirt-python and proxmoxer instead of
the provider. Nothing in `orchestrator/` was changed. The shipped
`vcows destroy` tears the result down, which is the compatibility check.

Rig: `qemu+ssh://vcows@vcows/system`, pool `images`, libvirt 11.10.0 on the
host, libvirt-python 11.1.0 on the dev box, QEMU 10.2.2, OpenTofu 1.12.6,
dmacvicar/libvirt 0.9.8, proxmoxer 2.3.0. No Proxmox cluster is reachable from
the dev box, so the Proxmox half was run by the operator from a package
(section 4) against PVE 8.4.0, node `cows-dev-host`, bpg/proxmox 0.111.1, and
its results are M4. Evidence is in `/home/ssullivan/tofu-eval/evidence/`, one
directory per measurement; every number below came from a file there.

## 1. Verdict

**Points at option 3 for libvirt and Proxmox.** Whether that is option 2 or 3
overall is the vSphere create, which #198 names as where the provider earns
most and which nothing here measures; #196's rig spike is where that number
comes from.

The deciding measurements:

- M1: 179 lines of create for libvirt and 111 for Proxmox, both under the
  200 the prediction allowed, replacing 371 and 296 lines of HCL.
- M2: the libvirt VM boots, takes its address, carries the marker verbatim,
  and the shipped destroy removes it.
- M4: on PVE 8.4.0 the `import` upload goes through the API on a token alone,
  the VM comes up, and the shipped destroy removes it. The SDK path is 6 s
  slower than the provider there, where it waits on tasks.
- M6: `just scan` goes green on the no-tofu image with nothing new accepted.
  Today's image has 20 IDs outside the baseline, every one on a Go binary.
- M5: 74.5 MB less on the wire, 198 MB less unpacked.

Two things the SDK path has to carry that the provider carries today, both
measured in section 3: the golden-image upload on libvirt (28 lines, both
stream modes) and `requests_toolbelt` on Proxmox (one EPEL RPM, without which
proxmoxer buffers a whole upload in memory and refuses anything over 2 GiB).

## 3. What the SDK path carries that the provider carried

Measured on the libvirt side, in b1:

- **The upload.** 14 lines dense, 14 more for the sparse stream. `pool.createXML`
  at the file's size, `conn.newStream`, `vol.upload`, `stream.sendAll` over a
  raw fd, `stream.finish`. The sparse variant needs SEEK_DATA/SEEK_HOLE and the
  `[in_data, length]` protocol libvirt-python's `sparseSendAll` expects; it
  earned nothing on this image and costs nothing on a dense one, so it is a
  flag. Spike A4 holds: the declared capacity is overwritten by the header, and
  the overlay is where `disk_bytes` goes.
- **The domain XML.** 43 lines of template mirroring `main.tf`'s
  `libvirt_domain.vm` block by block, including the firmware exclusivity the
  module's `os` block comments explain. libvirt validated it at define; the
  provider's schema validation, and `tofu validate` with it, is what goes.
- **One connection scheme.** The C client cannot use `sshcmd`, so
  `connection_uri(target)` with the default transport serves preflight, create
  and destroy alike. The two-scheme split in `render.py` is a provider fact and
  leaves with it.
- **No plan, no state.** The provider's plan preview and per-resource state
  were never read by anything: destroy works by marker and the run directory's
  `plan.json`/`apply.json` are artifacts. b1 prints one timed line per resource
  as the run's record instead. A failure raises with the resource named and
  rolls nothing back, which is also what the provider does; `preflight.orphan_volumes`
  is what sees the leftovers, as now.

On the Proxmox side, in b2, run once against PVE 8.4.0:

- **`requests_toolbelt`.** proxmoxer's HTTPS backend streams a multipart body
  only through `requests_toolbelt.MultipartEncoder`; without it a file over 10
  MiB is read into memory and one over 2 GiB raises `OverflowError`. Not in the
  venv today, not in the image. `python3-requests-toolbelt` 1.0.0 is in EPEL 10
  and is in the package image.
- **The multipart filename.** PVE names the uploaded file after the part, and
  proxmoxer takes that from the file object's `name`, so the golden image is
  opened as an `io.FileIO` and renamed to `base_volume_name` rather than copied.
- **Resize after import.** `import-from` gives the disk the image's own
  virtual size; the provider hides a `resize` to `disk_gb` behind `size`. b2
  reads `scsi0` back, resizes when larger, refuses when smaller (PVE cannot
  shrink). `resize` returns a UPID on current PVE and nothing on older ones;
  both are handled.
- **`nextid`.** Two deploys racing for a vmid is the same race the provider
  has; nothing here changes it.
- **`import` through the upload API** is a PVE version fact: the endpoint took
  only `iso` and `vztmpl` before `import` content was added. PVE 8.4.0 accepted
  it (M4). A cluster that refuses it makes token-only create impossible without
  SSH, and that alone would keep the provider on Proxmox; the provider itself
  uploads `import` the same way, so it would be no better off.
- **The task wait is the cost.** Five UPIDs per VM through `api.wait` against
  the provider's three; M4 puts the whole gap there. `POLL_INTERVAL` was set
  for stops and deletes, where one second did not matter.

Neither script has tests. That is the cost #198's option 2 names: a backend
off tofu loses `tofu validate` and the `.tftest.hcl` files (711 lines across
both) and needs its own create-path tests. `tests/fake_libvirt.py` already
has the connection, pool and domain shapes; it would gain `createXML`,
`newStream`, `defineXML` and `setAutostart`. `tests/fake_proxmox.py` would
gain `upload`, `nextid`, `qemu.post`, `resize` and `status.start`.

## 4. The Proxmox call sequence, from the dry run

`b2_proxmox_create.py --dry-run` renders as if the image were not yet on the
cluster and prints what it would send, against nothing:

```
POST /nodes/pve/storage/local/upload {"content": "import", "filename": "tofueval-base.qcow2"}
POST /nodes/pve/storage/local/upload {"content": "iso", "filename": "tofueval-p-seed.iso"}
GET  /cluster/nextid {}
POST /nodes/pve/qemu {"vmid": "100", "name": "tofueval-p", "description": "vcows: {...}\n",
     "bios": "ovmf", "machine": "q35", "onboot": 1, "cores": 2, "cpu": "host",
     "memory": 2048, "ostype": "l26", "scsihw": "virtio-scsi-pci",
     "scsi0": "local-lvm:0,import-from=local:import/tofueval-base.qcow2,discard=on,ssd=1",
     "ide2": "local:iso/tofueval-p-seed.iso,media=cdrom", "boot": "order=scsi0;ide2",
     "efidisk0": "local-lvm:1,efitype=4m", "net0": "virtio=52:54:00:7f:94:ef,bridge=vmbr0"}
GET  /nodes/pve/qemu/100/config {}
PUT  /nodes/pve/qemu/100/resize {"disk": "scsi0", "size": "20G"}
POST /nodes/pve/qemu/100/status/start {}
```

Every POST and the PUT return a UPID that goes through `api.wait`, the same
function `stop_vm` and `delete_vm` use. The package at
`/home/ssullivan/vcows-tofueval/` holds an image built from this branch with
tofu, `requests_toolbelt` and `docs/spikes/` inside, so the SDK path and the
shipped `vcows deploy` run from one image against one config; the imported
image was freed between the two halves so both uploaded. The run came back the
same afternoon and is M4; the sequence above is what PVE 8.4.0 received and
accepted, resize included.
